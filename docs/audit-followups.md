# Audit follow-ups

Пункты аудита, где сейчас сознательно сделан частичный/минимальный фикс, а не полное решение —
чтобы контекст решения не потерялся к моменту, когда до него дойдёт очередь. Каждый пункт живёт
здесь, пока не закрыт; закрытые — переносить в конец файла с датой закрытия, не удалять.

## Открытые

### Опрос статуса профилей — доделать унификацию на Остановке 4

- **Заведено:** 2026-09-04, по итогам аудита перед Остановкой 4.
- **Сделано сейчас:** `useVisionReady` переведён на `useQueries` (TanStack, функция-форма
  `refetchInterval`, поллинг останавливается сам, когда `ready: true`).
- **Оставлено как было:** `useScannerStatus` (ручной `setInterval` на фоновый статус +
  `confirmStopped` как императивный поллинг-цикл внутри `handleStopScanner`) и `useProfileActions`
  (четыре ручных `Record<string, boolean>` вместо `useMutation.isPending`) — не тронуты.
- **Почему не всё сразу:** `profiles-page.tsx` ещё заглушка, ни один из этих хуков реально не
  подключён — рано видно настоящие ограничения интеграции, риск переделывать дважды.
- **Обновление 2026-09-08:** Profiles подключена по-настоящему (реальная страница, не заглушка) —
  триггер ниже сработал, но саму унификацию поллинга ещё не делали, просто собрали страницу из
  того, что было. Актуально по-прежнему.
- **Проверить на Остановке 4**, когда Profiles подключается по-настоящему:
  1. Не рассинхронизировались ли между собой поллинг `useVisionReady` (теперь через query cache)
     и `useScannerStatus` (всё ещё вручную) — например, по частоте опроса одного и того же
     профиля из двух независимых источников.
  2. Стоит ли на этом этапе доделать вариант 2/3 из аудита (`useScannerStatus` → `useQueries`,
     `useProfileActions` → `useMutation`) — тогда уже будут видны реальные требования интеграции,
     решать по факту, а не заранее.
  3. `useScannerStatus` сейчас молча глотает ошибки поллинга в трёх местах
     (`initializeScannerStatuses`, интервал в `startPolling`, `confirmStopped`) — в Sentry сбой и
     так уже виден (репортится внутри `apiFetch` до того, как долетит до этих `catch`), но
     пользователь не видит ничего, строка тихо показывает последний известный статус как
     достоверный. При переводе на `useQueries` это должно решиться само через `isError`/
     `failureCount` — руками счётчик последовательных ошибок сейчас не пишем.
- **Связанная находка:** аудит spy-frontend, «Опрос статуса реализован дважды — на TanStack Query
  и вручную через setInterval».

### useProfileActions — довести pending-состояния до useMutation на строку

- **Заведено:** 2026-09-07, по итогам аудита перед Остановкой 4.
- **Сделано сейчас:** копипаст `set → spread → delete` в четырёх хендлерах (`handleRunVision`,
  `handleStopVision`, `handleRunScanner`, `handleStopScanner`) вынесен в один локальный хук
  `usePendingIds()` внутри `useProfileActions.ts` — дублирование убрано, архитектура не менялась.
- **Не сделано:** `useMutation` на само действие. Причина — `useMutation` даёт корректный
  независимый `isPending` только когда вызван **на строку** (одна мутация — один профиль), а не
  централизованно на всю страницу, как сейчас устроен `useProfileActions`. Двигать его в
  `VisionButtons`/`ScannerButtons` есть смысл только вместе с переводом `useScannerStatus` на
  `useQueries` (пункт выше) — иначе `startPolling`/`confirmStopped`/`isScannerRunning` всё равно
  останутся колбэками, и получится половинчатый гибрид.
- **Обновление 2026-09-08:** Profiles подключена, реальные требования интеграции теперь видны —
  можно делать этот пункт вместе с унификацией поллинга выше, когда дойдут руки.
- **Проверить на Остановке 4:** делать оба пункта (`useScannerStatus` → `useQueries` и
  `useProfileActions` → `useMutation` на строку) одним заходом, когда видно реальные требования
  подключённой страницы Profiles — не по отдельности.
- **Связанная находка:** аудит spy-frontend, «useProfileActions вручную ведёт четыре карты
  pending-состояний».

### Profile — решить DTO+adapter при реальном подключении Profiles

- **Заведено:** 2026-09-07, по итогам аудита перед Остановкой 4.
- **Сделано сейчас:** удалён мёртвый тип `ActiveVisionProfile` (нигде не использовался —
  `fetchActiveVisionProfiles` реально возвращает `ActiveProfilesResponse` из
  `api/vision-browser/index.ts`, никак не связанный с ним). `Profile.name` сделан опциональным —
  синхронизировано с тем, как его уже трактует `profile-selector.tsx`
  (`profile.name ?? profile.id`) и локальная тень типа в `profile-table-row.tsx`.
- **Не сделано:** DTO+adapter для `is_received`/`profile_name`/`port` — эти поля сегодня не
  читает ни один компонент/хук, а тип, судя по всему, скопирован из старого Next.js-приложения при
  переносе на Остановке 2 и не сверялся с реальным ответом бэкенда. Заводить адаптер под
  неиспользуемые и неверифицированные поля — то же самое «не заводить сервис без явной
  необходимости», что и в остальном проекте.
- **Проверить на Остановке 4:** когда `/api/vision/folders/:id/profiles` реально начнёт
  использоваться на странице Profiles — свериться с фактическим ответом бэкенда и тогда решить,
  нужен ли `ProfileDto` + `mapProfileDtoToProfile` (camelCase `isReceived`/`profileName`) по
  образцу `Post`, или поля вообще не те, что сейчас в типе.
- **Обновление 2026-09-08:** сверила с реальным кодом бэкенда (`getVisionProfiles` в
  `spy/apps/backend`) — `is_received`/`profile_name`/`port` действительно приходят именно так, тип
  точный. Но по-прежнему ни один из них не отображается в UI (таблица показывает только `id`/
  `name`) — DTO+adapter пока так и не нужен, просто теперь это подтверждённый факт, а не
  предположение.
- **Связанная находка:** аудит spy-frontend, «Profile и ActiveVisionProfile — ровно тот случай,
  под который заведён DTO+adapter, но без него».

### src/api/auth — единственное исключение из паттерна проброса ошибок

- **Заведено:** 2026-09-08, по итогам аудита перед Остановкой 4.
- **В чём дело:** `login`/`verifyToken` в `src/api/auth/index.ts` ловят `ApiError` сами и
  возвращают `{ success: false, error }`, а не пробрасывают её вверх, как все остальные
  `src/api/*`. Решение объяснимое (форме логина нужен текст ошибки инлайном, без тоста), но это
  единственное такое место в кодовой базе.
- **Почему не сделано сейчас:** первый план был просто пометить это комментарием в коде — не
  подходит, комментарии в коде не нужны. Нужно либо решить, что расхождение и так видно из кода и
  ничего не трогать, либо оформить иначе (например явным типом результата вместо try/catch внутри
  файла) — решение отложено, не текущая приоритетная задача.
- **Проверить:** когда в следующий раз будем трогать `src/api/auth` или добавлять вторую форму с
  похожей логикой — решить окончательно, а не откладывать снова.
- **Связанная находка:** аудит spy-frontend, «src/api/auth — единственный файл, где ошибка не
  бросается, а гасится в объект ответа».
